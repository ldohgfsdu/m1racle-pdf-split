# M1racle PDF Split v1.0.0-verify

按页区间 / 章节 / 等分拆 PDF 的安卓小工具，第一版 release 包。

本仓库从 M1racle Reader 独立出来，与阅读器共享 0 行代码：不依赖 EPUB、批注、Room、阅读器 UI。
引擎是 PDFBox-Android 2.0.27.0，界面 Jetpack Compose。

## 功能

### 1. 按区间拆

输入 `1-5,8,12-20` 这类表达式，支持开放区间（`-20`、`100-`）与倒序自动归一化。
解析器是纯 Kotlin，14 个用例覆盖边界（空串、单页、重叠、越界、非法分隔符）。

### 2. 按章节拆

读 PDF 内嵌书签（outline）自动成段；书签缺失时按页数启发式切分。
同时读页面标签（page labels），让 `i, ii, 1, 2` 这类罗马数字前言不被打乱。

### 3. 等分拆

每 N 页一段，或固定 M 段。按页数降序派发，避免长尾任务拖在最后。

### 4. 保真

- 页面几何全量复制：MediaBox / CropBox / BleedBox / TrimBox / ArtBox / Rotation / UserUnit
- 继承资源物化（`materializeInheritedResources`）：拆开后页面不丢父节点上的字体与图形状态
- 页面内链重映射：原书第 87 页跳到第 12 页，拆段后目标仍指向段内正确页
- 注释、文本层、外链 URI 保留
- 输出走 SAF：同名冲突自动避让，不覆盖既有文件

### 5. 失败可观测

每段拆完先做内存校验，落盘后再回读校验；某段失败能精确定位到起始-结束页，不会出现「整体失败但不知道哪一页坏了」。

## 这一版最值得说的一件事：加载慢 20 倍的真相

一份 420 页 / 988 MB 的扫描教材，默认加载要 **104 秒**。不是文件大，也不是磁盘慢：

| 模式 | 加载耗时 |
| --- | --- |
| 默认（lenient） | 104.45 s |
| 关闭宽松解析（strict） | 5.11 s |

根因在那份 PDF 的交叉引用流：3,163 条记录里有 **21 条写着「在用」但偏移是 0**。
PDFBox 的宽松校验碰到第一条就否决整张表，退回逐字节暴力重扫 1.04 GB：

```
Stop checking xref offsets as at least one (3074 0 R) couldn't be dereferenced
Replaced read xref table with the results of a brute force search
```

其余 1,717 条偏移复核后**全部指向正确位置，0 条解引用失败**。因此能说的只有一句：**文件存在结构异常，但绝大多数有效对象的偏移是正确的**；这不等于「文件没坏」——异常记录本身就构成缺陷。

方法级采样剖析显示，热点 91.7% 的 self time 落在 `RandomAccessBuffer.read / seek / peek / isEOF / isString / rewind`，有效扫描速率约 30 MB/s，而顺序读能到 2.2 GB/s —— 这是纯 CPU 在烧，不是 I/O 在等。

**但这一版没有把 strict 设为默认。** 快 20 倍不等于结果一样：那 21 条记录里的 3095、3106、3148 仍被页面 3093、3104、3146 当作 XObject 引用，而对象本身不存在。strict 关掉了部分自动修复，必须逐页验证才能判断它有没有静默丢内容。

## 所以多了第二个入口：A1 校验

桌面上的「A1 校验」就是为这件事造的验证台：

1. 同一源文件、同一页码规划、同一输出设置，lenient 与 strict 各全量拆一遍（`L-*` / `S-*` 前缀）
2. strict 整本失败时自动逐段重试，把失败精确点到第 1-20 / 21-40 段
3. 对**落盘产物重新打开**取指纹逐页比对（不复用拆分时的内存对象，避免自证）：几何、内容流 SHA-256 与字节数、资源字典逐条（含对象号与解析状态）、注释、内链目标页 / 外链 URI、文本层 SHA-256
4. strict 侧资源缺失清单：记录源文件对象号、引用页、以及该名字是否真被内容流（含一层 Form XObject）`Do` 调用 —— 用来区分「悬空引用没人画」和「页面真掉图」
5. 输出 `A1-验证报告-<时间戳>.txt` 与 `.json`，同时备份到 app 外部目录 `a1-verify/`

防假阳性：每页算一个「证据不足」标记（任一侧内容流取不出、或两侧资源字典都为空）。`weakPages > 0` 时「完全一致」不作为内容正确的证据。

PC 侧还有独立于 PDFBox 的比对脚本 `tools/a1-render-diff.py`，用 poppler 灰度渲染后先字节比对、差异页再算像素差与墨量。

### 关于「同体积、不同哈希」

早前版本说这是「构建时间戳」导致 —— **该说法已被自己的实验否证**，此处更正并给出实测：

- ZIP 内 200 个条目的时间戳**全部相同**（固定 `1981-01-01 01:01:02`），不存在时间戳抖动。
- 同一目录、同一源码、同一命令连续三次干净构建：`classes.dex`（2,678,128 B）与 `assets/dexopt/baseline.prof` **逐字节相同**，200 个条目里只有 `META-INF/version-control-info.textproto` 不同（它记录嵌入的 git 修订号，`c3174bc` → `c539384`）。说明这条构建链在这些配置下是确定性的，差异只来自 VCS 戳。
- 改用 reader 的编译策略做对照（`kotlin.compiler.execution.strategy=in-process`、`workers.max=1`、关并行）：`classes.dex` 仍与上述三次一致 → **编译策略与并行度不是差异来源**。
- 与 `1.0.0-14-verify`（在 reader 仓库作为子工程构建）相比，`classes.dex` 与 `baseline.prof` 都不同（长度相同、内容不同），VCS 元数据也不同（120 B vs 42 B）。**具体成因尚未定位**，只能确定不是时间戳、也不是编译策略。

结论：字节数相同**不能**作为二进制等价的证据。两个包是否行为等价，只能靠真机安装与 A1 逐页比对来回答，本文不作「等价」声明。

## 已知问题

- 对象 3095 / 3106 / 3148 被页面 3093 / 3104 / 3146 当作 XObject 引用，但对象不存在 —— 这是**已确认的悬空资源引用**；这三页是否存在可见内容缺失**尚未验证**，待 A1 逐页比对给出结论。此处不做「本就缺图」的断言：目前证据只能证明引用无法解析，不能证明画面少了东西。
- strict 下全 420 页的产物一致性结论，待 A1 报告回传后固化；在那之前 strict 只是可选路径
- 扩展测试集（正常 PDF / 损坏 xref / 增量更新 / 对象流 / 加密）尚未覆盖，strict 失败时的行为没有系统验证
- 加密 PDF 尚未支持
- `A1 校验` 会往目标目录写约 2 倍源文件体积的产物（两套拆分包），测完记得清
