按页区间 / 章节 / 每份页数拆 PDF 的安卓小工具。这一版把上一版验证过的「快速加载路径」真正接进了生产。

## 这一版改了什么

上一版（1.0.0-verify）用 A1 验证台证明了一件事：关掉 PDFBox 的宽松解析（`isLenient = false`）能把加载从 57.5 秒压到 2.7 秒，420 页逐页语义指纹完全一致。但当时**没有**把它设成默认 —— 快 20 倍不等于结果一样，必须逐页验证过才敢上。

那个验证做完了，于是这一版把结论做成了机制，而不是口号：

```
PdfStructureScanner.scan(file)      独立的 xref 扫描器，不依赖 PDFBox，1 GB / 15~40 ms
  → 严格加载                         PDFParser(isLenient = false)
  → 逐页可达性探测                    页树 + 内容流解码 + 坏引用核对
      fatal → 关闭重开宽松解析
      clean → 采用严格（快速路径）
```

不是「全局 `setLenient(false)`」，是**有条件启用的快速路径**。

### 三层判据：什么情况才允许回退

首版把「资源解析为空」一律判 fatal，结果这本教材照样回退到宽松解析（60,391 ms）—— 因为那 21 条坏记录里有 1 条恰好被某页的资源字典引用着。优化被自己的判据抵消掉了。

改成按「坏引用是否真被画出来」分层：

| 情形 | 判定 | 理由 |
| --- | --- | --- |
| 页树 / 内容流无法解析 | **fatal** | 解析本身坏了 |
| 引用指向坏对象，且该名字被内容流 `Do` 绘制 | **fatal** | 宽松会重扫找到、严格不会，等于真丢图 |
| 引用指向坏对象，但从未被 `Do` 绘制 | **soft** | 不参与渲染，A1 已证明产物逐页相同 |
| 引用指向从未声明的对象（两种解析器都返回 null） | **soft** | 源文件本身如此，与加载模式无关 |

绘制判据是对解码后的内容流跑 `/([A-Za-z0-9_.+#-]{1,64})\s+Do\b` 收集被绘制名，再与坏引用名比对。

### 接入范围

5 个会完整加载一次文档的入口全部统一走 `PdfBoxSetup.open(file, LoadMode.AUTO)`：probe、正文扫描、书签读取、页码标签、拆分 worker。**拆分算法一行未动。**

### 界面直读

源文件卡片现在直接告诉你走了哪条路、花了多久：

```
PDF · 420 页 · 988 MB · 有书签 · 快速解析 2.9s
```

文件结构有异常时，提示条按实际路径分别措辞，不再一律说「已走兼容解析」：

> 文件结构异常：交叉引用表 3163 条记录中有 21 条指向偏移 0，但没有任何一页真正绘制它们，已正常走快速解析；拆分结果不受影响。

真发生回退时才显示：

> ……且被页面实际引用，已自动切换到兼容解析；拆分结果不受影响，但解析会比正常文件慢。

## 真机实测（Xiaomi 25098PN5AC / Android 16）

样本：`src.pdf`，420 页 / 1,035,745,318 B（988 MB），纯图像型，每页 1 张 JPEG，600 ppi。

决策日志原文：

```
probe stageMs=594 loadMs=2887 loadCpuMs=3220
  decision=[strict scanMs=15 zeroOffset=21 badHeader=0 entries=3163 softMiss=1
            first=第 15 页 XObject/COSName{KSPX1} 引用了坏对象 3148，但未被绘制]
  xref kind=STREAM startxref=1035741885 valid=true entries=3163/3163 inUse=2705
       zeroOffset=21 badHeader=0 objStream=967 unverified=0 encrypted=false prev=false
```

| 指标 | 上一版（宽松） | 本版（AUTO/严格） | 倍数 |
| --- | --- | --- | --- |
| 加载 | 57,537 ms | **2,887 ms** | **19.9×** |
| 独立扫描器 | — | 15 ms | — |
| 整轮 probe（含建缓存） | — | 3,673 ms | — |

`zeroOffset=21` 没有触发回退，`softMiss=1` 正确识别出「第 15 页 `/KSPX1` → 坏对象 3148，但未被绘制」—— 判据按设计工作。

拆分（`concurrency=1`，每份 20 页，21 段 / 420 页），两次独立运行：

| 运行 | 版本 | 结果 | 总耗时 |
| --- | --- | --- | --- |
| 1 | 1.1.0 | `finished=21/21` | 7,926 ms（worker 加载 3,068 ms / STRICT） |
| 2 | 1.1.1 | `finished=21/21` | 6,560 ms（worker 加载 2,541 ms / STRICT） |

## 产物正确性：不用 PDFBox 自己验自己

加载路径的复验不能再用 PDFBox 做裁判。改用 **poppler 25.07.0（`pdfimages`）** 抽取源文件与 21 个产物的全部内嵌图像，逐张比字节。

该教材 420 页对应 **423 个图像流**（第 15、328 页各多 1 个 `smask`）。

| 检查项 | 结果 |
| --- | --- |
| 图像结构表（类型 / 宽 / 高 / 色彩空间 / 分量 / bpc / 编码 / 流字节长度） | 423 条 **逐条一致，差异 0** |
| 图像流字节 SHA-256 | 423 张 **逐张一致，差异 0** |
| 覆盖图像流总长 | ≈ 0.96 GiB |
| 页数与页面尺寸 | 21 × 20 = 420 页，均 1124.28 × 735.12 pts，与源一致 |

1.1.0 与 1.1.1 两版产物各自独立跑通这两条判据，两次产物总字节数也完全相同（1,030,595,782 B）。

### 一个必须记住的否定结论

**拆分产物的整包 SHA-256 天生不可复现。** PDFBox 保存时会写入随机 trailer `/ID`，同一输入跑两次，整包哈希必然不同。

本轮开发时就踩了这个坑：拿整包哈希对比两版产物，21/21 全部不同，差点当成回归事故上报。换成图像流哈希后差异立刻归零。

所以：整包哈希不能用来判断「两次拆分是否一致」，也不能当回归基线。有效判据只有页级 / 流级指纹（A1 的语义指纹），或者像本报告这样用独立解析器抽取比对。

## 已知问题

- **同目录已有同名产物时，会自动追加 `_2` 序号**（避让策略）。属预期行为，但它依赖系统媒体库的可见性：如果你用 shell 删了文件、应用还看到旧记录，本轮产物就会带 `_2`。
- probe 会对每一页解码内容流做可达性检查，本机 `stageMs=594`。页数更多、内容流更复杂的文件需要再测，必要时做按需化（只解码含坏引用的页）。
- 扩展测试集（正常 PDF / 损坏 xref / 增量更新 / 对象流 / 加密文件）仍然只有这一本真实样本，没有合成样本矩阵。
- 加密 PDF 尚未支持。
- `A1 校验` 诊断台仍在包内，会往目标目录写约 2 倍源文件体积的产物，测完记得清。
