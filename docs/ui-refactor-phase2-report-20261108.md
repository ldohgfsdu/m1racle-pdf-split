## 5. 真机验收中发现并已修复的缺陷

这三个问题只有在真设备上才会暴露：

1. **完成状态不可见**：拆分成功后界面回到「预计生成 1 个 PDF」，与未开始时完全一样。→ 新增「完成」区块（文件数、保存位置、文件列表），主按钮变「再拆一次」。
2. **重复执行生成 `(1).pdf`**：因为看不到完成，我点了两次；第二次时目录里已有同名文件，SAF provider 在名字后自动加 ` (1)`，而预览是按旧快照算的。→ 拆分前重新读取目录并 `OutputPlanner.avoidExisting`，改名结果同步回预览。
3. **切换模式后「完成」卡片残留**：→ `setMode` 重置 `RunState`。

## 7. 技术与质量

- 引擎写盘路径、并发调度、页校验逻辑**未改动**（`PdfRangeSplitter` 仅新增拆分前目录刷新）。
- 新增 `OutputPlanner` / `OutlinePlanner` / `ConcurrencyPolicy` / `PdfPageLabels` / `PdfProbe` / `SafOutputDirectory`，全部为纯逻辑或薄 IO，可单测。
- `SavedStateHandle` 只保存：模式、页码原文、每份页数、输出目录 URI、深度校验开关。**不保存** `parts`、任务快照、进度。
- SAF 权限持久化：源文件 `takePersistableUriPermission(READ)`，输出目录 `READ|WRITE`。

## 8. 未完成项（明确声明）

**部分成功与重试机制未实施。**

当前引擎仍是 `coroutineScope` + `async` 的「全有或全无」：任一任务抛异常会取消其余任务并删除本次已创建的全部 SAF 文档。

按批准的执行顺序，这属于第 5 步、需独立实施与独立回归。本轮为了先把 UI 与解析层落地并完成真机验收，没有动它。**这意味着：多文件拆分中途失败时，已成功的文件会被一并删除，用户需要重来。** 这是当前最大的已知短板。

## 9. 已知问题与风险

| 系统目录选择器的自动化点击 | 小米 Android 16 的 documentsui「使用此文件夹」按钮对 `adb input tap` 无响应（人工点击正常）。验收时靠一次成功的点击 + 系统恢复完成，非应用缺陷 |
