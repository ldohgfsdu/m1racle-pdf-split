## 三、这套 AUTO 加载机制在干什么（读懂这三段即可）

PDFBox 默认宽松解析，遇到一条坏 xref 记录就否决整张表、退回逐字节暴力重扫 —— 1 GB 文件要 57 秒。严格解析只要 3 秒，但可能静默丢内容。

`LoadMode.AUTO` 的做法：先用不依赖 PDFBox 的独立扫描器看 xref，再严格加载，再逐页探测「有没有页面真正需要的东西解析不出来」，有问题就回退宽松。

判据抽在 `FastPathGuard.kt`（纯函数，可 JVM 单测）里，核心不对称是：

> **断言"这个资源被绘制了"永远安全；断言"没人绘制它"只有在证据完整时才安全。**

据此形成的分层：

| 情形 | 判定 |
| --- | --- |
| 页树 / 内容流（数组任一项）/ 已声明资源字典解析失败 | fatal |
| 坏引用，且无法确认它未被绘制（内容流截断、`Do` 计数不配对、嵌套 Form 超深） | fatal |
| XObject 坏引用，且完整的绘制扫描确认它没被使用 | soft（保留快速路径） |
| xref 扫描不可信（失败 / 格式认不出 / 条目没全检查 / 有未验证条目 / `/Prev` 链不完整 / 加密 / `/XRefStm`） | 否决，直接走宽松 |

## 八、几条来之不易的认知，别重复踩

- **拆分产物整包 SHA-256 天生不可复现**（PDFBox 保存写随机 trailer `/ID`）。整包哈希不能判同一性、不能当回归基线，只能用页级流级指纹或独立解析器（poppler）比对。曾因此差点把正常差异当回归事故。
- **走 lenient ≠ 慢 20 倍**。57 秒只出现在 xref 有坏记录、触发暴力重扫时；健康文件走 lenient 也是几百毫秒。所以"否决快速路径"的代价通常可忽略。
- **单测通过 ≠ 真机行为正确**。有两处实现层假阴性（`PDResources(stream)` 取错字典、`/Contents` 解析不出流被当成空）在单测层面完全不可见，只有真机矩阵才暴露。
- 本机 `df` / `Win32_LogicalDisk` 报 D: 可用 0 字节是**假报**（实际可写约 2.4 GB），判断余量要 `dd` 实测。
