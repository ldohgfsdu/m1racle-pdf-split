## 4. 已确认根因

1. **并发是负优化**：`PdfRangeSplitter` 每个 worker 各自 `PdfBoxSetup.load(sourceFile)` 打开一份完整 `PDDocument`（PDFBox 的 `PDDocument` 非线程安全，当前是"每 worker 一文档"）。加载耗时 93~137 秒且互相抢 I/O；拆分本身 <5s。加并发只是多烧 CPU（482s → 749s）、同样撞 95°C 热节流，**用时完全不变**。
2. **加载慢的真正代价在 scratch，不在读源文件**（复核新增）：`PdfBoxSetup.memorySetting()` 用的是 `MemoryUsageSetting.setupTempFileOnly()`，即所有 COS 对象都落到 `cache/pdfbox-scratch` 的临时文件。988MB 文档 × 6 个 worker ≈ **5.9 GB 内部存储写入 + 回读**，这才是 93~137 秒和 I/O 互相踩踏的来源（源文件本身只被顺序读一次，`stage ms=1234` 就是证据）。
   - 推论：单 worker 时该代价降到 ~1/6，但仍是"把整本 988MB 抄一遍"；**方案 C 应该先试 `setupMixed()`（主内存 64~256MB + 余量落盘）**，而不是去优化 staging。
   - 该推论**未实测**，属待验证假设，别当结论用。
3. **取消卡几分钟**：旧代码 `destination.save(sink)` 是一次性阻塞写盘，期间无任何检查点；UI 状态又只在任务抛异常后才更新。10 版已加每写一次检查 + `ensureActive()` 检查点（`PdfRangeSplitter.kt:132/296/377/420/429/441/491/518`）与 `SplitViewModel.cancel()` 先改 UI 再取消 job，**但尚未真机验证**。

### P0-2b　关于"换引擎"（决策记录，别重复讨论）
外部调研（pdq / MuPDF / qpdf）给的基准是**"文档已加载后拆页"的速度**（pdq 12,732 页拆单页 37ms~、qpdf 4.7× 慢）。本项目实测：21 段真正干活只要 **4 秒**，瓶颈 133 秒全在**打开**。
→ 结论：**现在换引擎解决不了当前问题**，而且 MuPDF 是 AGPL、pdq 很新无 Android 集成验证。顺序必须是 C（改 memory setting）→ A（并发收敛）→ B（共享文档）；三者都试完仍有 >60s 落差，才值得评估换引擎。换引擎的前提是**先有 420 页原件**（P0-0）。

### 12.2 54 秒是什么（逐项排除）
在 debug 包里对**同一份真文件**（复制进 app 私有目录）测 `PDDocument.load`，拆开 load 与建页树：

| 设置 | loadMs | pagesMs | scratch 写入 | 线程 CPU | 页数 |
|---|---|---|---|---|---|
| `tempFileOnly` | **91,888** | 0 | 1,037,303,808 B | 91,384 ms | 420 |
| `mixed128` | 104,254 | 2 | 903,080,080 B | 103,082 ms | 420 |

（debug 包整体比 release 慢约 1.9 倍：release 实测 54.4 s ↔ debug 91.9 s，比例自洽。）

排除项，全部有数：
- **不是 I/O**：同一路径顺序读 **2.2 GB/s**、4K 随机块 **1.4 GB/s**；私有目录写 **2.0 GB/s**；1 GB 设备内复制 1.4 s。989 MB scratch 写入只值 0.5 s。
- **不是并发争抢**：这一轮 concurrency=1，只有一次 load。
- **不是文件损坏**：`startxref` ×1、`%%EOF` ×1，单 xref、单 EOF，结构完好。
- **不是页树**：`pagesMs=0~2`。
- **是纯 CPU**：`wall ≈ threadCpu`，且换内存策略只改动十几秒，不改量级。

**结论：PDFBox 解析这份 988 MB / 420 页教材本身就要几十秒 CPU。**
同一套代码、同量级的合成文件（pdfunite 拼的 926 MB / 399 页）只要 **3.0~4.1 s** —— 差 20 倍，所以差别来自这份书的对象结构，不是体积、不是路径、不是调度。

## 13. 方法级采样诊断结论（2026-11-08 17:10）

完整报告：**`PDF拆分-加载热点诊断-20261108.md`**（含 trace 原始文件清单，位于 `output/pdf-split-ui-20261108/prof/`）

一句话：**慢的不是 PDF 解析，是 PDFBox 的 xref 修复路径；根因是 21 条「in-use 但偏移=0」的 xref 条目，让整表被判不可信，触发 1.04 GB 逐字节重扫。**

关键数据：

| 模式（同文件 tempFileOnly） | loadMs |
|---|---|
| lenient（当前生产） | 139,144 / 104,450 / 102,971（三次） |
| **strict（`setLenient(false)`）** | **5,110** |
| **strict + mixed128** | **4,649** |
| 合成件 926 MB / 399 页 lenient | 3,771 / 4,201 |

- 日志原文：`Stop checking xref offsets as at least one (3074 0 R) couldn't be dereferenced` → `Replaced read xref table with the results of a brute force search`（tag `PdfBox-Android`）。
- 全表复核：1,717 条普通对象偏移 **100% 正确**；21 条 offset=0：`1690 2642 3074 3076 3084 3087 3092 3094 3095 3103 3105 3106 3114 3119 3124 3136 3139 3143 3147 3148 3156`。
- 其中 3095 / 3106 / 3148 被 3 个页面（3093 / 3104 / 3146）当 XObject 引用，而对象在文件中**不存在** → 这 3 页现有实现下本来就缺图。
- 字节层占 self 91.7%（read 26.1 / seek 19.8 / peek 12.6 / isEOF 9.5 / isString 6.0 / rewind 5.1）；有效扫描速率 ~30 MB/s，而顺序读 2.2 GB/s、私有目录写 2.0 GB/s → 慢在 CPU 不在磁盘。

优化三档（详见报告 §4）：
- **A1 strict + 失败回退**：实测 20.4×；**阻塞项**＝strict 下全 420 页拆分的产物一致性未验证（3 个页面的悬空 XObject 是否抛异常）。
- **A2 在 cache 副本尾部追加修正 XRef 流**（把 21 条改 free）：保留 lenient 容忍度，预期与 A1 同级，未实施。
- **A3 probe 按需化**：省 58.6 s/次选文件（已实测，已批准暂缓）。
- 换引擎（MuPDF/pdfium）：**现阶段不建议**——5 s 里约 78% 是 989 MB 拷进 scratch 的必要动作，换引擎只剩 2–3 s 可省，却要付 JNI + AGPL 成本。

注意：以上全部为 debug 包数据；同文件 release 54,437 ms ↔ debug 91,888 ms，倍率 1.69×，故 release 下 strict 预计约 3 s（**估算未实测**）。
